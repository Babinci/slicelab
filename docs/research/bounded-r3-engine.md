# Bounded synchronous R3 scheduler checkpoint

This describes the engine implementation and the measurements available on 2026-11-01. It is not a 32-voice R3 acceptance or a hard realtime deadline guarantee.

`prepareScheduled` preallocates the request, MIDI, UI-command, meter and planar audio rings. A callback captures the published view, parameters, routing and MIDI before it advances the oldest request. The collector scans the call hazard, request hazards, acquisition/retained hazards, and voice hazards in handoff order. Requests are processed in timestamp order, so a later note-off cannot remove older, unrendered audio. Finished PCM is returned exactly one fixed latency later. The default is `ceil(sampleRate * .020)` frames, raised if the prepared maximum host block is larger. Requested positive latencies are retained exactly; only ring capacities are rounded up.

The scheduled renderer retains the MIDI/segment/voice cursor across callbacks. Each R3 input, R3 output retrieval, source-generation, or mix step is limited to 128 frames. Configuration setters and reset each have their own step. All voices share a global operation ceiling and a monotonic-time cutoff at 65% of the nominal host block period. This time cutoff is a soft guard, not a guarantee: an indivisible operation already in progress, operating-system preemption, event capture and copying can exceed the remaining time. R3's `final=true` can internally drain many windows in one call, so the scheduled path instead feeds bounded zero chunks after the slice end and stops when its logical source interval ends. Direct/Repitch and stretched output share the same delay in realtime and offline mode.

The realtime callback rejects a block larger than its prepared maximum, too many MIDI records, exhausted bounded rings, failed view capture or missing due PCM. It returns silence, clears pending requests and note/sustain state, increments `scheduledOverloads()`, and restarts with a fresh latency interval. Later notes must be retriggered. Offline oversized callbacks are split without a delay change. Zero-frame events remain ordered. No sample, command or asset ownership is destroyed on the callback.

## Measured on the local machine

The release binary used the repository's pinned Rubber Band 3.3.0 static build, FFTW/libsamplerate backend and queue-reset reuse patch. The behavior run in `local/verification/scheduled-engine-tests.log` passed 20 checks: exact neutral and Repitch delay, MIDI onset and release, R3 realtime/offline and mode-transition equality, pending-view and parameter capture, retirement, overflow recovery, realtime/offline oversize handling, independent pitch/duration, one-frame tails, and 32 voices in offline processing. A later check also asserts the 960-frame default at 48 kHz. These tests do not establish concurrent reclamation safety under sanitizers.

At 20 ms latency, the 300-callback, single-voice benchmark exercised ratios and pitch scales 0.25, 1 and 4 (excluding neutral 1/1) at 44.1, 48 and 96 kHz, for 128- and 512-frame blocks. The recorded runs had zero scheduler overloads and nonzero output; see `local/verification/scheduled-engine-grid.log` and `local/verification/scheduled-engine-rates.log`. At 48 kHz, ratio 1 and pitch +7 semitones, the first run measured 128-frame p99 0.56 ms and max 2.01 ms; 512-frame p99 2.12 ms and max 2.70 ms. These are short benchmark results, not proof under all load.

The fixed 20 ms does not satisfy simultaneous 32-voice R3 startup on this machine. In the 48 kHz +7-semitone test, 2, 4 and 8 voices passed at 128 frames; 16 and 32 triggered fail-silent recovery. At 512 frames, 2 and 4 passed; 8, 16 and 32 triggered recovery. Thirty-two neutral direct voices passed at both block sizes. Exact results are in `local/verification/scheduled-engine-poly.log` and `local/verification/scheduled-engine-benchmark.log`. This is a material limit on the requested 32-voice feature, not a supported polyphony cap or a substitute for further optimization.

The sustained-voice discriminator used the same engine instance and first rendered 9,600 frames offline before switching to realtime callbacks at 48 kHz/512 frames. Two and four +7-semitone voices sustained 300 callbacks without overload (p99 2.39 and 4.83 ms). Eight voices overloaded on callback 104; 32 overloaded on callback 1. See `local/verification/scheduled-engine-warm.log`. Preparing startup state alone cannot resolve that measured sustained 32-voice deficit.

An individual `R3Stretcher::process` call with 128 input frames was also measured using the pinned release library. Across the 48 kHz ratio/pitch grid, the first run's p99 ranged approximately 0.38–2.17 ms and its maximum 2.76–5.07 ms. A later run recorded a maximum 9.06 ms. These wall-clock observations include operating-system scheduling. The 48 kHz/128 period is 2.67 ms, so the present API call cannot establish a hard 128-frame bound. At 96 kHz/128 frames, the period is 1.33 ms; several measured whole callbacks exceeded it even though the scheduler overload count was zero. A zero overload count is not proof of a glitch-free host callback.

## Remaining gates

- Positive-controlled allocation and deallocation hooks must surround the complete processor callback, including `malloc`, `calloc`, `realloc`, `free`, `posix_memalign`, `aligned_alloc`, C++ `new` and `delete`. The pinned library's separate reset/processing grid is not a whole-processor test.
- Test the 192 kHz rate, variable and one-frame realtime blocks, rate and layout changes, extreme automation, additional MIDI and UI overflow cases, and 64 output channels. Verify deterministic view handoffs and concurrent publication under ASan/TSan.
- Improve or explicitly constrain 32-voice stretched startup and steady throughput; the current fail-silent behavior reports failure but does not meet full 32-voice R3 playback. A smaller input quantum alone cannot split an individual FFT analysis window.
- Rebuild and test the actual VST3 in REAPER with fixed PDC, monitoring, anticipative playback, offline rendering, project restore and the real sample. Measure XRUNs and callback wall time independently of the overload counter.
